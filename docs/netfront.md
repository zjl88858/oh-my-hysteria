# NetFront：主流量与游戏风格的小包副路

NetFront 从 [OMHY v1.3.0](release-v1.3.0.md) 起可选，使用 v1 线格式。名字来自曾用于游戏掌机的浏览器。它借用的是一种**通信布局**：同一服务器上，一路持续传数据，另几路有的成小串出现、有的只偶尔响一下。它不解析游戏、语音或聊天内容，也不实现游戏服务或反作弊协议。

## 配置

主路减少大流停顿的模式另见 [NetFrontLite](netfrontlite.md)。两者使用各自的认证密钥和配置段，不能混配。

假设服务端主端口是 UDP 443：

```yaml
# 服务端的顶层配置；客户端改为 server: example.com:443
listen: :443

# 下列部分在客户端和服务端相同
obfs:
  type: netfront
  netfront:
    password: "REPLACE-WITH-AT-LEAST-32-RANDOM-BYTES"
    extraPorts: [31011, 31012, 31013]
```

- `password` 接受 32～1024 个原始 UTF-8 字节。混淆密码与 `auth` 分开。保持正常 TLS 验证和两端时钟同步。
- `extraPorts` 必填 **2 或 3** 个不同的 UDP 端口（1～65535），不能包含主端口、范围或 `0`。顺序标识副路，两端要对应。服务端绑定与主监听相同的地址和地址族；客户端每路使用独立的临时源端口，并沿用客户端的 socket 设置。
- 服务端防火墙、安全组、容器和端口映射都要放行这些 UDP 端口。一个本地端口绑定失败，启动即报错并释放已开的端口。域名、证书和 `server` 仍只需一份。
- 只支持固定的主端点；不与端口跳跃、Realms 或 Mimic 组合。分享链接使用 `obfs=netfront`、`obfs-password`、`netfront-extra-ports=31011,31012,31013`。`share` 会自动对查询参数转义。

## 什么时候走副路

主路按 [Presto](presto.md) 的规则分片、填充并选择突发间隔。另从同一密码派生副路的角色排列：两条时是短暂活跃的“语音型”和稀疏的“心跳型”，三条时多一条偶发成组的“聊天型”。每个方向分别派生目标包长、抖动、组长和间歇。新会话用新的随机会话 ID 抽样，发送端看的是**当前是否有业务、该路是否已验证、这一组是否已到发送时间，以及当前帧能否装下**。接收端无需同步这个随机过程。

到了一次副路机会，如果当前的 Presto 帧足够小，就把这一帧装进副包；接收端取出来，仍交给同一个 Presto 重组和去重窗口。否则先发送原来的主包，成功后才附发一个无业务小包。不复制正常发送成功的数据，也没有为凑比例持续运行的空闲心跳。QUIC 自己的保活属于真实输入。

| 边界 | v1 的行为 |
| --- | --- |
| UDP 载荷大小 | 内层 QUIC 1～1200 B；主路最多 1232 B；副路最多 384 B |
| 路径与封装成本 | 副路有 83 B 的独立认证封装，另外有可变填充；数据副包包含已认证的整片 Presto 帧 |
| 自主副包的预算 | 每次至少消耗此前 4 个成功主包、8 倍本次副包长度的主路字节额度；最多积存 8 包和 3072 B 额度。这是上限，不是目标比例 |
| 验证回包 | 服务端每个有效请求至多答一次，回复不大于请求；它单独计数，不由服务端业务额度生成 |
| 关闭或丢包 | 单次副路 socket 写入最多等 25 ms（调用方更早的写截止时间优先）。本地副路写失败时，同一数据帧可从主路重发。若写成功后在网上丢失，照常由内层协议处理；没有外层重传 |

## 为什么副路不会变成另一条 QUIC 连接

1. 客户端先经主路建立认证状态。服务端只认在主路已经收齐过数据的当前客户端会话；随机小包不能在副端口新建会话。
2. 客户端有业务时，用副端口发认证请求。服务端核对会话和客户端 IP，从**收到请求的那个 socket** 向实际源端口返回随机的 128 位挑战。同一路只接受递增的请求号，接受两次请求至少相隔一秒。
3. 客户端从预期服务端 IP 和端口收到匹配的挑战，随后发出的数据或无业务小包都带回该挑战。服务端验证成功才允许把普通回包从这条路发出。证明与会话、方向、端口序号及实际对端地址相绑定；复制到别的端口不能开通路径。
4. 交给 QUIC 的永远是**主端点地址**。即使 NAT 给不同副路分配了不同的外部源端口，也不会触发 QUIC 路径迁移。不同副路仍须使用同一个客户端公网 IP。不支持主端点在活动会话中换地址。

服务端的路径许可最长 20 秒，持续有流量时客户端会提前重新验证。同一地址上，上一代已验证凭证最多还能接收 2 秒的在途包，且不超过原到期时间；它不能用于发包或验证新路径，副路地址改变立即撤销。一个从未打通的副端口不会承载业务；已验证的副路突然中断时，识别失效前可能丢掉少量小包。此时主路仍可用，UDP 应用数据没有可靠交付保证。单纯连通主端口不能证明副路已工作。

## 线格式与资源

HKDF-SHA256 的 salt 是 `oh-my-hysteria/netfront/v1`。`presto-root` 派生主路所用的独立密码，普通 Presto 和 NetFront 配同一用户密码不能互通。`side/client-to-server` 和 `side/server-to-client` 分别派生 XChaCha20-Poly1305 密钥；`roles` 与 `shape/<方向>` 单独派生调度规则。

副包为 `nonce[24] || AEAD(头 || 可选的 Presto 帧 || 随机填充)`，AAD 是两个字节：副路总数、从 1 开始的副路序号。43 B 加密头依次是：类型 1 B（1 请求、2 挑战、3 数据、4 无业务）、主路客户端发送会话 ID 16 B、该路请求号 8 B、挑战 16 B、内嵌帧长度 2 B；整数为大端。每次发送（含重试）使用新随机 nonce。副路不能通过嵌入别的发送会话来创建或替换主路路由。

所有端口共用 Presto 的主会话、重放和重组资源上限。副路状态随主会话释放；每个 socket 组只有一个主路接收队列（32 项）、一个副路接收队列（16 项），以及服务端最多 16 项的待发挑战。副路认证另限全局 8192 次/秒、64 个来源桶各 2048 次/秒，副路噪声不消耗主路的验签额度。诊断接口 `NetFrontStats()` 按端口报告实发包数、字节、数据包、无业务包和成功验证次数。

## 如何理解验证结果

**v1.3.0 采用已通过代理功能验收的 `.2` 实现。** 在 Windows → Linux VPS 的公网应用测试中，两副路和三副路都完成了 HTTP 网页访问、HTTPS CONNECT 文件下载、SOCKS5 HTTPS 上传及 SOCKS5 UDP DNS 查询。下载和上传的摘要均与源站匹配。另在六轮短连接对照中，两种配置的主端口分别占总包数的 91.47% 和 87.92%，两组都观察到了双向真实副路数据。这是特定负载的计数，不是目标比例。反复连接、续期、断路恢复及弱网下的 UDP 回显数据见[完整报告](network-test-netfront-2026-11-20.md)。

`go test ./extras/obfs ./app/cmd -run NetFront -count=1 -v` 可复现本机端口收发、路径绑定、配置、TLS 和代理传输测试。`TestNetFrontTrafficShapes` 固定模拟时钟与输入、只换密码及会话；`TestNetFrontLoopbackPorts` 则使用真正的 UDP socket，分别验证副路可达、丢弃副路包、端口顺序错配时的数据完整性。

在同样的 6000 次模拟输入下，密码样本 0 的一个会话在三条副路上分别发了 **156 / 29 / 157** 包；仅换会话后是 **142 / 30 / 156**。密码样本 1 的第一个会话则是 **209 / 131 / 15**。这是已验证路径上的调度器计数，不含验证握手，也不是公网实测比例。

Windows 回环测试在 IPv4（3 条副路）和 IPv6（2 条）上均完成了正常证书校验、64 KiB TCP 往返与 32 条 UDP 往返。两个同 IP、同密码的客户端共用一个监听器时也分别收回了自己的数据。见[代理功能与传输验证](network-test-netfront-2026-11-20.md)。

这些测试能说明流量怎样分布，不能证明观察者会把它分类成游戏。多端口之间的关联本身也可能成为特征。目前没有真实游戏流量对照，不能据此声称它比 Presto 更难识别。
