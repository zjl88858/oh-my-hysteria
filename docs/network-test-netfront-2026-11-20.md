# NetFront 候选：代理功能验收（2026-11-20）

**结论：`v1.2.1+netfront.2` 的两副路、三副路配置均通过代理功能验收，其实现纳入 [OMHY v1.3.0](release-v1.3.0.md)。** 在指定的较差公网线路上，页面能打开、文件能下全、上传内容一致，代理 DNS 能得到正确答案。本文的数据与 SHA256 属于当时实测的候选程序；v1.3.0 分发包使用自己的 `SHA256SUMS`。

## 应用实际上做了什么

Windows amd64 上启动候选程序的 HTTP 和 SOCKS5 监听器；只有这个程序连接 Linux amd64 VPS。网页、文件和 DNS 源站只绑定在 VPS 的回环地址，应用不能从公网直接访问它们。两端使用正常证书校验及 BBR standard。每种配置各开一次冷连接，一次连接同时供两个代理入口使用。

| 使用方式 | 验证内容 | 2 个副端口 | 3 个副端口 |
| --- | --- | --- | --- |
| HTTP 正向代理 | 打开服务端临时生成的网页；校验 HTTP 200 和页面 SHA256 | 通过 | 通过 |
| HTTP `CONNECT` → HTTPS | 校验源站证书，通过 TLS 1.3 下载随机 24 KiB 文件，对照源站 SHA256 | 通过 | 通过 |
| SOCKS5 `CONNECT` → HTTPS | 上传独立随机 16 KiB；源站实际收到的长度及 SHA256 与客户端一致 | 通过 | 通过 |
| SOCKS5 `UDP ASSOCIATE` → DNS | 校验 SOCKS 回包地址、DNS 事务号、问题和 A 记录 `192.0.2.7` | 首次发送成功 | 首次发送成功 |

HTTPS 下载、SOCKS5 上传和 DNS 查询并发进行。两次均只建立 **1 条** OMHY 连接，源站各记录一次页面、一次文件、一次上传和一次 DNS 应答。另在 VPS 内先用回环校准了同一套测试。

## 这次修了什么

第一版副路续期时会立即撤销旧凭证。若合法数据已经发出、却比续期请求晚到，它可能在无网络丢包的条件下被丢弃。回归测试复现了这个顺序。候选 `.2` 允许在**同一会话、同一副路和同一实际地址**上限时接收上一代已经验证的在途包：最多 2 秒，且不超过原许可到期时间。旧凭证不能用于发包、开通新路径或续命；地址改变立即撤销。线格式没有改变。

这个问题不能解释第一轮 `.1` 不到 9 秒的公网冒烟结果。旧客户端配新服务端、新客户端配旧服务端的回环检查均为 72/72；要在两个接收方向都得到续期修复，应两端一起升级。错误 CA、错误代理登录凭证和错误混淆密码均未建立可用代理。

## 重复连接与稳定性

- **公网传输对照：** 3 个密码、每个 2 轮，每轮交替测试 Presto、NetFront 两副路和三副路，共 18 次冷连接；另做 2 次跨续期的持续负载。**20/20** 都完成代理握手，并在同一个 TCP 流上通过前后两段内容校验。NetFront 的每条配置副路都观察到了双向认证后的活动；持续负载中三条副路各观察到 **3 代**完成双向验证的许可。
- **差速与断路：** Windows 四条回环路径的单向延迟分别设为 65 / 12 / 115 / 35 ms，无注入丢包时 180/180 个 UDP 回显均正确。活动会话中再切断全部副路 25 秒，恢复时更换三个副路的源端口：原 TCP 流跨中断完成，三条副路重新验证；384 个 UDP 请求全部到达源站，返回 383 个。转换期外预定稳定窗口为 140/140。
- **多客户端与轮换：** 两个同 IP 客户端共享监听器，并发传输各自的随机内容，Presto、两副路和三副路三个场景均完成每客户端上、下行各 2 MiB 校验。另用真实 UDP socket 连续跑 **10 分 15 秒**：20,500/20,500 次回显通过，两个方向均实际跨过十分钟发送会话轮换。这个长测发生在本机，不是十分钟公网测速。
- **回归：** Windows 三个 Go 模块测试通过；NetFront 定向 race 重复 3 轮通过；Linux amd64 上的 NetFront / Presto 定向测试重复 3 轮通过。Linux arm64 产物为交叉编译，未在 ARM 机器上执行。
