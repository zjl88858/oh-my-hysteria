# 专用 VPS 首轮网络验证

日期：2026-10-29（北京时间，UTC 2026-10-28）。本报告区分 Linux 回归、
受控网络与真实公网结果，**不作为算法排名或生产可用性保证**。
本轮没有实现 BBRv3，也没有修改控制器或默认拥塞算法。

## 环境与约束

- VPS：Ubuntu 24.04.4 LTS，Linux 6.8.0-134，amd64，KVM，1 vCPU、约 2 GiB 内存。
- 两端应用：当前工作区编译的 `oh-my-hysteria v1.0.0` release。
- Linux 回归工具链：官方 Go 1.26.0，下载后按官方 SHA256 校验。
- 所有本轮 QUIC 网络实验均启用 Gecko，参数保持默认，未尝试裸 QUIC 回退。
- 公网客户端文件名严格为 `oh-my-hysteria-windows-amd64.exe`，使用用户按进程
  配置的中国大陆分流；没有用 Python / curl 等进程直发 VPS UDP 来替代该线路。
  地理位置未独立验证。
- 对 `test-omhy.todspod.si` 成功完成 Let's Encrypt HTTP-01 签发，客户端正常
  校验证书链与 SNI。因本机分流 DNS 返回合成地址，客户端显式连接 VPS IPv4，
  不关闭证书验证。
- 两端省略 `bandwidth`，服务端 `ignoreClientBandwidth: true`；认证结果
  `tx: 0`，不使用 Brutal。BBR 使用 standard profile。
- 公网与受控吞吐实验串行运行，不与 Go 编译 / race 检查同时进行。

## 受控网络：45/45 双向传输通过

工具：[tests/network/gecko_bench.py](../tests/network/gecko_bench.py)。三个网络
命名空间模拟客户端 → 路由器 → 服务端，不设默认路由或 NAT，不修改公网接口
qdisc。两方向各 100 ms 传播延迟、10 Mbit/s TBF；三种场景为：

1. 浅队列：上限约为 50 ms 链路速率的字节数。
2. 深队列：约 400 ms。
3. 每方向 0.1% 随机丢包，队列约 100 ms；同时影响数据与 ACK。

每场景五种配置，各三轮，按种子 9406 打乱顺序；每次下载、上传各 4 MiB，
共 360 MiB 有效负载，全部留在 VPS 内部。空载大部分 ping 样本约 200 ms，
初始个别样本约 400 ms。每次传输精确校验两方向完成记录和字节数。

下面是三次结果的中位数，单位 **Mbit/s**，每格为 **下载 / 上传**：

| 配置 | 浅队列 | 深队列 | 随机丢包 0.1% |
| --- | --- | --- | --- |
| BBR standard | 8.05 / 7.80 | 8.49 / 8.11 | 8.24 / 7.73 |
| CUBIC legacy | 8.50 / 8.11 | 8.65 / 3.75 | 7.00 / 2.31 |
| CUBIC HyStart++ | 8.50 / 7.92 | 8.62 / 3.75 | 8.55 / 8.16 |
| Reno legacy | 8.62 / 8.10 | 8.65 / 3.04 | 3.89 / 7.29 |
| Reno HyStart++ | 8.51 / 8.08 | 8.62 / 3.04 | 8.33 / 5.73 |

**不能据此声称 HyStart++ 在丢包网络显著优于 legacy。** 每格仅三个样本，
内核随机丢包并未固定序列；例如 CUBIC legacy 的丢包场景上传范围为
2.19–8.05 Mbit/s，波动明显。

更重要的是，工具先下载、再在**同一条 QUIC 连接**上传。上传继承前阶段的 RTT、
控制报文、窗口和慢启动状态，并非独立冷启动。深队列中 legacy 与 HyStart++
均出现明显的上下行差异，需要新连接的单方向测试才能进一步解释，不能简单
归因于 HyStart++。深队列传输期间的 ICMP RTT 曾接近 600 ms，但该观测包含
握手和阶段间隙，不等同于纯满载 QUIC RTT。

功能通过也不能证明每次实验都进入了 CSS；CSS 状态转换由确定性单元测试覆盖，
本轮没有控制器内部状态轨迹。参数和更多局限见
[测试工具说明](../tests/network/README.md)。

## 公网：保留一次未解释的长传输超时

1. Gecko + BBR 的 1 MiB 上下行冒烟测试通过。
2. 最初计划做每方向 4 MiB 的三轮五配置对照：第一条 BBR 样本完成，下载
   10.77 Mbit/s、上传 11.66 Mbit/s；紧接的 CUBIC HyStart++ 样本达到
   120 秒超时，编排停止。
3. 单独诊断的 CUBIC HyStart++ 256 KiB 下载完成，平均约 0.746 Mbit/s。

上述事实不足以确定超时是线路丢包、实现缺陷还是其他因素。没有把单个 BBR
样本当作整组完成，也没有将超时样本排除后宣称 CUBIC 稳定。

初版公网编排在超时时没有把内存捕获的过程输出写盘，因此该失败只保留了
`TimeoutExpired`、配置与时限证据，不能重建当时的传输阶段或吞吐。随后修正
测试工具，使过程日志直接落盘；没有改动应用来掩盖该失败。

初版 UDP echo 探测也没有充分忽略迟到的旧序号回复，超时后可能连带误计后续
包；其 `3/16` 未匹配不能作为公网真实丢包率。后续探测按序号等待并忽略旧包。
TCP echo 的中位 RTT 约 251 ms，仅反映当时的少量应用层往返样本。

### 补充短传输：12/15 完成，异常不只属于 HyStart++

修正编排后，改为每方向 1 MiB、每次进程最多 45 秒，仍是五配置各三轮且打乱
顺序。这是另一组短传输，**不能与前组 4 MiB 样本合并统计**。12 次完成，
2 次客户端初始化超时，1 次进程达到 45 秒时限。失败均保留过程日志。

下表仅对完成样本求中位数，单位 Mbit/s；存在失败删失，不能只看速度忽视分母：

| 配置 | 完成 / 尝试 | 下载 | 上传 | 未完成情况 |
| --- | --- | --- | --- | --- |
| BBR standard | 3 / 3 | 4.73 | 5.49 | 无 |
| CUBIC legacy | 2 / 3 | 0.214 | 5.73 | 一次 45 秒超时 |
| CUBIC HyStart++ | 2 / 3 | 0.254 | 5.82 | 一次初始化超时 |
| Reno legacy | 3 / 3 | 0.256 | 4.00 | 无 |
| Reno HyStart++ | 2 / 3 | 0.264 | 5.50 | 一次初始化超时 |

原有内置 Reno 的下载也明显变慢，因此不能把现象直接归因于新增 CUBIC 或
HyStart++。两次初始化错误均为 `connect error: timeout: no recent network
activity`，未得到测速记录；该路径还未在客户端安装所选控制器，不等同于
证明 HyStart++ 的数据阶段失败，服务端当时状态仍需更细轨迹。

修正后的 BBR echo 探测中，16 次 TCP 小报文往返中位数约 234 ms，16 次 UDP
echo 均匹配，中位数约 236 ms；样本少，不能宣称公网无丢包。

### 独立调试：观察到服务端拥塞窗口退避

另外用 1 MiB 双向 CUBIC HyStart++ 传输开启两端 `QUIC_GO_LOG_LEVEL=debug`。
该次完成，下载约 0.270 Mbit/s、上传约 6.13 Mbit/s。调试开销使其不能混入
正式吞吐表。日志中观察到：

- 服务端 66 条判丢包事件、3 次 PTO 日志（包含握手阶段）。
- 服务端 377 条 congestion-limited 日志，可见窗口从约 44.9 kB 以下收缩至
  **2882 字节**，接近两个最大报文；不是仅等待应用提供数据。
- 客户端没有判丢包日志，仍有 PTO；两端末尾平滑 RTT 约 230–234 ms。

这为“下载发送端在反复拥塞退避”提供了直接证据；该诊断样本仍在传输，而非
永久停住。但 QUIC 判丢包可能包含 PMTU 探测、重排或误判，日志条数不等于
真实链路丢包率，也不能据此确认 ISP、分流、GFW 或控制器的最终责任。
初始 120 秒超时仍未被单独复现并解释。

### 真实转发完整性

五种配置各用本机转发端口连接 VPS 的 localhost echo 服务，避免以内置测速
替代全部真实 TCP 转发验证。每种发送并回显 512 KiB 数据，五种 SHA256 校验
全部通过。UDP 每种只探测四个序号：BBR、CUBIC legacy 各匹配 3/4，其他
三种各匹配 4/4，合计 18/20；未匹配按三秒时限计，迟到旧序号不冒充成功。
样本过少，不能据此估计稳定丢包率或判定某个算法的 UDP 优劣。
